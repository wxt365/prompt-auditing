## 后续实施：连接失败原因持久化

2026-10-27：在既有 `error_code` 字段保存固定分类，不新增字段或迁移数据库：

| 错误代码 | 含义 |
| --- | --- |
| `upstream_dns_error` | 上游域名解析失败 |
| `upstream_connection_refused` | 上游拒绝连接 |
| `upstream_tls_error` | TLS 握手或证书校验失败 |
| `upstream_timeout` | 上游连接、响应头或响应体等待超时 |
| `client_canceled` | 当前请求上下文被取消，请求取消或客户端断开 |
| `upstream_error` | 其他或未细分的失败，不能可靠确定具体原因 |

分类依据为 Go 错误链、当前请求上下文以及标准 `httptrace` TLS 握手回调，不按错误字符串猜测。Windows 原生套接字的拒绝连接错误单独兼容。DNS 或 TLS 阶段超时优先归为超时；上游内部单独返回 `context.Canceled`，而当前请求未取消时，不归因于客户端。

连接失败的结果仍为 `upstream_error`；收到响应后中断仍为 `upstream_stream_error`。当前请求取消且导致转发失败时，结果为 `client_canceled`。已有上游 HTTP 错误结果不变。返回给客户端的通用错误代码及 502/504 状态保持兼容；已经收到上游状态的响应体失败仍保留该状态。

审计列表显示中文分类，详情增加“失败原因”。实时日志同步分类；关闭实时采集后仍保存审计分类，退出后可查询。持久化不保存原始网络错误字符串、认证头或请求正文，避免诊断中混入凭证。旧记录不会重写，原有通用错误显示“原因未细分”。

## 已确认的问题

### P1：文本规范化产生大量临时分配

位置：`internal/security/normalize.go` 的 `normalizeWithMapping`，`internal/security/engine.go` 的 `inspectKeywords`。

每条关键字规则分别规范化全文，并为规范化字节建立原文区间映射。不区分大小写时，当前实现在每个规范化片段上调用 `folder.String`。代表性规则基准中，1 MiB 文本单次累计分配约 581 MB、耗时约 234 ms；5 MiB 单次累计分配约 2.91 GB、耗时约 1.13 秒。

1 MiB 样本内存分析中，`golang.org/x/text/transform.String` 占累计采样分配约 92.2%，经由 `normalizeWithMapping` 的累计分配约占 99.6%。这已经是有测量依据的优化项，不再只是从源码推测。

建议：先优化规范化过程，减少逐片段大小写折叠产生的临时对象；对不改变字节长度的 ASCII 文本使用可验证的直接偏移路径；在同一检测阶段按大小写选项复用规范化结果。必须保留 Unicode NFKC、大小写折叠、原文位置映射、先替换后检测和重叠选择的原有语义，再用同一基准比较优化前后。正则预编译可以随后做，不应把注意力仅放在正则编译上。

### P1：上游 4xx/5xx 被持久化为“已完成”

位置：`internal/gateway/proxy.go` 的 `forwardUpstreamError`。

上游返回错误状态后，只要错误响应正文能被安全处理并成功写给客户端，就使用 `result = completed`、空错误码。审计界面据此显示“已完成”，虽然上游状态码仍保留。实时日志会根据状态码标记失败，两种日志因此解释不一致。

建议：区分“响应转发完毕”和“请求业务成功”。上游错误状态使用独立的失败结果，保留原始 HTTP 状态和安全处理后的响应；补充普通和 gzip 错误响应的审计结果回归测试。

### P1：持久化错误信息不足以区分连接失败原因

位置：`internal/gateway/proxy.go` 的 `forward`、`complete`，`internal/audit/models.go`，`internal/storage/audit_query.go`。

DNS 失败、连接被拒绝、TLS 错误、超时等在审计库中都只留下 `upstream_error`。脱敏后的具体连接错误只写入可选的内存实时日志；未提前开启采集或退出程序后，无法仅靠审计记录还原具体原因。

建议：用稳定错误分类保存 DNS、连接、TLS、超时及客户端取消等原因，必要时附加长度受限、凭证脱敏的诊断。不要把完整请求或原始认证头作为诊断保存。数据库增加字段应走正式迁移，旧记录维持未知，不能凭当前配置补写历史。

### P1：首次启动缺少“尚未配置”的明确状态

位置：`internal/settings/store.go` 的 `Open`，`internal/app/desktop.go` 的 `desktop`，`internal/app/web/app.js` 的 `refreshStatus`。

新环境默认保存公共上游地址，并在客户端认证模式下自动启动代理。顶部“代理运行中”仅代表本地服务和审计正常，没有检测上游可用性。离线环境用户可能误以为已经可以调用模型，本次失败即发生在此配置状态。

建议：增加明确的首次配置状态，在用户确认并保存上游之前提示“请配置上游”；提供手动连接检查，并标明检查只验证网络/HTTP 可达性，不代表密钥、模型或完整协议一定可用。默认值和网络错误不应自动替换为某个固定内网地址。

### P2：保存设置或规则时，管理 API 会串行等待代理停止

位置：`internal/app/desktop.go` 的 `managementHandler`、`managementAPI`、`restart`、`stop`。

管理 API 持有同一个控制器互斥锁执行整个操作，包括数据库查询、响应写出及最长约 15 秒的代理停止等待。在此期间其他状态和实时日志查询也要等待。规则保存还会停止当前代理，可能终止正在进行的长流式请求。

已确认的是锁范围和重启行为；界面在高负载下的具体阻塞时长尚未测量。

建议：先拆分配置读写、代理生命周期、审计查询的职责，再缩小锁范围。规则引擎可考虑切换不可变快照，让已进入的请求使用原快照完成。仍应保证版本一致、保存成功后才生效，避免简单移除锁导致竞态。

## 其他值得优化的路径

1. `internal/security/engine.go` 的 `inspectRegex` 对每段文本重复编译同一正则，`inspectKeywords` 对每条规则重复规范化同一文本。可在创建不可变引擎时预编译规则，在单次检测中按大小写选项复用规范化结果。需要验证规范化映射、重叠选择、两阶段检查和取消超时的行为不变。
2. `internal/storage/database.go` 每次打开策略库都执行完整完整性校验；管理页查询规则也会走该路径。审计库较大时的启动耗时、规则库较大时的管理延迟应分别测量，再决定是否区分启动校验和日常查询连接。
3. 普通放行请求目前也保存决策和完成两条事件，写入使用同步 SQLite 事务。是否保留全部成功请求是产品策略，需要显式配置；不能为了减少写入而破坏“请求转发前审计必须成功”的边界。

其中规范化分配开销已有实测依据；完整性校验耗时及审计写入在更大数据量下的影响尚未分别量化。普通放行日志是否保留属于产品策略，不应在本轮分析中擅自修改。

## 性能测试结果

环境：Windows amd64、AMD Ryzen 5 5600G、Go 1.26.5。全部测试使用本机模拟上游和临时数据库，未调用真实模型服务，未读取用户认证信息，未改动正在运行的网关。

### 现有基线

| 场景 | 样本 | 结果 |
| --- | --- | --- |
| 1 MiB 文本、两条正则加私网规则 | 50 次 | 纯检测 P95 约 59 ms |
| 简短 SSE、内存模拟审计、无内容规则 | 50 对直连/代理样本 | 首字节额外延迟 P95 约 1 ms |

这两项原有测试没有包含预置的关键字替换/拦截规模，第二项也不包含 SQLite 写盘，因此不能单独用于评估实际使用开销。

### 新增代表性规则基准

新增文件：`tests/performance/representative_test.go`。使用独立测试词，模拟 16 组替换映射、36 个拦截词和两条正则；不依赖用户具体规则内容。以下为纯 ASCII、未命中的文本检测，使用 `-benchtime=3x`，属于短时基准。

| 文本大小 | 平均单次检测 | 累计分配字节/次 | 分配次数/次 |
| --- | --- | --- | --- |
| 64 KiB | 15.21 ms | 36,260,400 | 131,256 |
| 1 MiB | 234.08 ms | 580,944,834 | 2,097,356 |
| 5 MiB | 1,129.63 ms | 2,905,178,565 | 10,485,970 |

累计分配是单次操作在整个执行过程申请的总量，包含可被 GC 回收的对象，**不是进程常驻内存，也不是峰值内存**。本次没有测量峰值 RSS。真实多语言内容、命中密度、历史条目数和规则表达式不同，耗时也会不同。

### 新增真实审计和并发测试

64 KiB 请求，每次实际执行一处替换，开启实时采集，使用真实 SQLite `synchronous=FULL` 审计，并通过 HTTP/SSE 转发。本机模拟上游立即返回，每个场景 30 次请求，首字节时间包含请求构建后的网络发送、安全检查、转发前审计与本机上游响应。

| 接口 | 并发数 | 首字节 P95 | 本次批次吞吐 |
| --- | --- | --- | --- |
| Responses | 1 | 39.67 ms | 44.7 请求/秒 |
| Responses | 10 | 85.98 ms | 123.0 请求/秒 |
| Chat Completions | 1 | 60.38 ms | 39.0 请求/秒 |
| Chat Completions | 10 | 104.27 ms | 118.4 请求/秒 |

全部请求成功。测试等待完成事件写入，再核验持久化记录数量、替换动作、完成结果、上游状态以及审计健康状态。吞吐是这个短批次的结果，不代表持续运行上限；两个协议分别测量，不能据此认定某协议始终更快。

原始结果和采样文件位于 `dist/code-review-20261027/`：`performance.txt`、`benchmark.txt`、`profile.txt`、`allocations.txt`、`cpu.txt`，以及 CPU/内存采样文件。

### 后续性能验证范围

需要将性能测试保留为优化前后的可重复基准。下一阶段应补充：中英文混合长会话、图片和工具历史、规则数增长、1/5 MiB 请求在 10 并发下的延迟和峰值内存、超并发拒绝、慢上游与长时间 SSE、客户端取消后的连接回收，以及持续运行和日志库达到容量阈值后的清理。

现有功能测试已覆盖部分取消、超限和 SSE 正确性，但不能替代这些场景的持续负载测量。不宜直接用真实模型的生成耗时衡量代理开销，应先用可控制的本地上游隔离变量。

重复运行：

```powershell
go test -tags performance ./tests/performance -run '^Test' -count=1 -v
go test -tags performance ./tests/performance -run '^$' -bench '^Benchmark' -benchtime=3x -count=1 -benchmem
```
